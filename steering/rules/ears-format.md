## Overview

EARS (Easy Approach to Requirements Syntax) は、あいまいさを排除し、テスト可能な要件を記述するための構造化アプローチです。LabFlowプロジェクトでは、すべての機能要件はEARS形式で記述されなければなりません（Article IV: EARS Requirements Format）。

---

## 5つのEARSパターン

### Pattern 1: Ubiquitous（普遍的）

**構文**: `システムは、[要件] しなければならない`

**英語**: `The [system] SHALL [requirement]`

**用途**: 常に真でなければならない要件。条件やトリガーなしに常に適用される。

**例**:
```
✅ 良い例:
- システムは、すべてのユーザーパスワードをbcryptでハッシュ化しなければならない
- システムは、APIレスポンスをJSON形式で返却しなければならない
- システムは、TLS 1.3以上の暗号化通信をサポートしなければならない

❌ 悪い例:
- システムは安全でなければならない（あいまい）
- システムは高速でなければならない（測定不能）
```

---

### Pattern 2: Event-Driven（イベント駆動）

**構文**: `[イベント] が発生した場合、システムは [応答] しなければならない`

**英語**: `WHEN [event], the [system] SHALL [response]`

**用途**: 特定のイベントやトリガーに対する応答を定義する。

**例**:
```
✅ 良い例:
- ユーザーがログインに3回連続で失敗した場合、システムはアカウントを15分間ロックしなければならない
- ワークフロー実行が完了した場合、システムはメール通知を送信しなければならない
- ファイルアップロードが完了した場合、システムはウイルススキャンを実行しなければならない

❌ 悪い例:
- ユーザーがログインしたとき、システムは適切に対応しなければならない（あいまい）
```

---

### Pattern 3: State-Driven（状態駆動）

**構文**: `[状態] の間、システムは [動作] しなければならない`

**英語**: `WHILE [state], the [system] SHALL [response]`

**用途**: 特定の状態が継続している間に維持されるべき動作を定義する。

**例**:
```
✅ 良い例:
- ワークフローが実行中の間、システムは進捗バーを表示しなければならない
- ユーザーセッションがアクティブな間、システムは30秒ごとにハートビートを送信しなければならない
- データベース接続が確立されている間、システムはコネクションプールを維持しなければならない

❌ 悪い例:
- システムがビジーな間、ユーザーに通知しなければならない（「ビジー」があいまい）
```

---

### Pattern 4: Unwanted Behavior（望まれない動作）

**構文**: `[エラー/異常] が発生した場合、システムは [対処] しなければならない`

**英語**: `IF [error condition], THEN the [system] SHALL [response]`

**用途**: エラー処理、例外処理、異常系の動作を定義する。

**例**:
```
✅ 良い例:
- API呼び出しがタイムアウト（30秒）した場合、システムは最大3回まで自動リトライしなければならない
- データベース接続が失敗した場合、システムはエラーメッセージを表示し、5分後に再接続を試行しなければならない
- 入力データが不正な形式の場合、システムはバリデーションエラーと修正方法を表示しなければならない

❌ 悪い例:
- エラーが発生した場合、システムは適切に処理しなければならない（あいまい）
```

---

### Pattern 5: Optional Feature（オプション機能）

**構文**: `[機能/設定] が有効な場合、システムは [動作] しなければならない`

**英語**: `WHERE [feature enabled], the [system] SHALL [response]`

**用途**: 設定やライセンスによって有効化される機能を定義する。

**例**:
```
✅ 良い例:
- 21 CFR Part 11モードが有効な場合、システムは電子署名機能を提供しなければならない
- GraphRAG機能が有効な場合、システムはナレッジグラフ可視化を提供しなければならない
- 多要素認証が設定されている場合、システムはログイン時に認証コード入力を要求しなければならない

❌ 悪い例:
- プレミアム機能が有効な場合、システムは追加機能を提供しなければならない（何が追加されるか不明）
```

## パターン組み合わせ

複雑な要件は、パターンを組み合わせて表現できます。

### Event + Unwanted Behavior
```
ユーザーがファイルをアップロードした場合（Event）、
ファイルサイズが100MBを超える場合（Unwanted）、
システムはエラーメッセージを表示し、アップロードを拒否しなければならない
```

### State + Optional
```
エンタープライズライセンスが有効な場合（Optional）、
ワークフロー実行中の間（State）、
システムはリアルタイム監視ダッシュボードを表示しなければならない
```

## 要件ID体系

LabFlowプロジェクトでは、以下のID体系を使用します：

```
[カテゴリ]-[サブカテゴリ]-[連番]

例: DASH-MAIN-001, WKFL-EXEC-003, SECU-AUTH-002
```

## 優先度レベル

| レベル | 日本語 | 説明 |
|--------|--------|------|
| P0 | 必須（Critical） | MVPに必須。これがないとリリースできない |
| P1 | 高（High） | 重要だがMVP後でも可。Phase 2で実装 |
| P2 | 中（Medium） | あると良い機能。Phase 3で実装 |
| P3 | 低（Low） | 将来的に検討。バックログ |

## 検証方法の種類

要件ごとに、検証方法を明示します：

| 検証方法 | 説明 | 例 |
|----------|------|-----|
| 単体テスト | コードレベルの自動テスト | Jest、Vitest |
| 統合テスト | コンポーネント間の結合テスト | Testcontainers |
| E2Eテスト | エンドツーエンドの自動テスト | Playwright |
| 手動テスト | 人間による確認テスト | QAチーム |
| 負荷テスト | 性能・スケーラビリティテスト | k6、Locust |
| セキュリティテスト | 脆弱性スキャン | OWASP ZAP |
| ユーザビリティテスト | UXの評価 | ユーザーインタビュー |
| レビュー | 設計・コードレビュー | PR Review |

## 良い要件の特徴（SMART）

要件は以下の特徴を満たすべきです：

| 特徴 | 説明 | チェックポイント |
|------|------|-----------------|
| **S**pecific（具体的） | あいまいでない | 「適切に」「効率的に」を避ける |
| **M**easurable（測定可能） | 数値で評価できる | 時間、件数、割合を明記 |
| **A**chievable（達成可能） | 技術的に実現可能 | 制約を考慮している |
| **R**elevant（関連性） | ビジネス価値がある | ユーザーストーリーと紐づく |
| **T**ime-bound（期限付き） | いつまでに | フェーズ/優先度が明確 |

## よくある間違い

### ❌ 避けるべき表現

| 避けるべき | 理由 | 改善例 |
|-----------|------|--------|
| 「〜すべきである」 | 強制力が不明確 | 「〜しなければならない」 |
| 「適切に処理する」 | あいまい | 具体的な処理内容を記述 |
| 「高速に応答する」 | 測定不能 | 「500ms以内に応答する」 |
| 「ユーザーフレンドリー」 | 主観的 | 具体的なUI要件に分解 |
| 「必要に応じて」 | 条件が不明 | 明確なトリガー条件を記述 |
| 「など」「等」 | 範囲が不明 | 全ての項目を列挙 |

### ✅ 改善例

```
❌ 悪い例:
「システムは、エラー発生時に適切に対応しなければならない」

✅ 良い例:
「APIエラー（4xx/5xx）が発生した場合、システムは以下を実行しなければならない：
  1. エラーログを記録（タイムスタンプ、エラーコード、リクエストID含む）
  2. ユーザーにエラーメッセージを表示（エラーコードと推奨アクション含む）
  3. 5xx エラーの場合、Slackアラートを送信」
```

## 要件テンプレート

新しい要件を追加する際は、以下のテンプレートを使用してください：

```markdown
| ID | EARS形式要件 | 優先度 | 検証方法 |
|----|-------------|--------|---------|
| [カテゴリ]-[サブカテゴリ]-[連番] | [EARSパターンに従った要件文] | 必須/推奨 | [検証方法] |
```

### 記述例

```markdown
| ID | EARS形式要件 | 優先度 | 検証方法 |
|----|-------------|--------|---------|
| SECU-AUTH-001 | システムは、パスワードをbcrypt（コストファクター12）でハッシュ化しなければならない | 必須 | 単体テスト |
| SECU-AUTH-002 | ユーザーがログインに5回連続で失敗した場合、システムはアカウントを30分間ロックしなければならない | 必須 | 統合テスト |
| SECU-AUTH-003 | 多要素認証が有効な場合、システムはログイン時にTOTPコード入力を要求しなければならない | 推奨 | E2Eテスト |
```

## レビューチェックリスト

要件レビュー時に確認すべき項目：

### 形式チェック
- [ ] EARSパターン（5種類のいずれか）に従っている
- [ ] 要件IDが正しい体系に従っている
- [ ] 優先度が設定されている
- [ ] 検証方法が明記されている

### 内容チェック
- [ ] あいまいな表現がない（適切に、効率的に、など）
- [ ] 測定可能な基準がある（時間、件数、割合）
- [ ] 単一の要件が1つの機能のみを記述している
- [ ] 実装方法ではなく「何を」するかを記述している

### トレーサビリティチェック（Article V）
- [ ] ユーザーストーリー/ビジネス要件に紐づいている
- [ ] 設計決定（ADR）に反映されている
- [ ] テストケースにマッピングされている
