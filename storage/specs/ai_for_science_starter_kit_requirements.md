## 1. 文書概要

### 1.1 目的
本文書は、AI for Scienceに初めて取り組む研究者向けのStarter Kit（以下「本システム」）の機能要件を、EARS形式で定義する。

### 1.2 EARS構文パターン

| パターン | 構文テンプレート | 用途 |
|----------|-----------------|------|
| **Ubiquitous** | システムは [動作] しなければならない | 常に適用される基本要件 |
| **Event-driven** | [トリガー] の場合、システムは [動作] しなければならない | イベント発生時の要件 |
| **State-driven** | [状態] の間、システムは [動作] しなければならない | 特定状態での要件 |
| **Optional** | [機能が有効] の場合、システムは [動作] しなければならない | オプション機能 |
| **Unwanted** | [望ましくない条件] が発生した場合、システムは [動作] しなければならない | 例外処理 |
| **Complex** | [条件A] かつ [条件B] の場合、システムは [動作] しなければならない | 複合条件 |

### 1.3 要件ID体系

```
[カテゴリ]-[サブカテゴリ]-[連番]
例: DASH-AUTH-001 = ダッシュボード-認証-001番
```

| カテゴリコード | 意味 |
|--------------|------|
| DASH | 統合ダッシュボード |
| WKFL | ワークフローテンプレート |
| DATA | データ前処理 |
| MODL | モデルカタログ |
| LERN | 学習モジュール |
| VISZ | 可視化ツール |
| COLB | コラボレーション |
| SECU | セキュリティ |
| PERF | 性能・スケーラビリティ |
| HELP | 初心者サポート |
| KNOW | 知識抽出・GraphRAG |
| SCRN | スクリーニング・フィルタリング |
| ITER | 反復的発見フロー |
| MLAB | My Lab Data（研究チーム知識ベース） |
| EXPT | 実験計画最適化 |
| UNCE | 不確実性定量化 |
| EXTD | 外部データベース連携 |
| HYPO | 仮説生成支援 |
| EXPL | 説明可能性（XAI） |
| PUBL | 論文・特許執筆支援 |
| MMDA | マルチモーダルAI |
| PLUG | プラグインアーキテクチャ |

## 2. 統合ダッシュボード要件（DASH）

### 2.1 認証・アクセス管理（DASH-AUTH）

#### 2.1.1 認証プロバイダー（マルチプロバイダー対応）

| ID | EARS形式要件 | 優先度 | 検証方法 |
|----|-------------|--------|---------|
| DASH-AUTH-001 | システムは、以下の認証プロバイダーを環境設定で切り替え可能としなければならない：ローカル認証、Microsoft Entra ID、Shibboleth | 必須 | 設定切替テスト |
| DASH-AUTH-002 | ローカル認証が有効な場合、システムはメールアドレスとパスワードによる認証を提供しなければならない | 必須 | 認証テスト |
| DASH-AUTH-003 | Microsoft Entra ID認証が有効な場合、システムはOAuth 2.0/OpenID Connectによるシングルサインオンを提供しなければならない | 必須 | SSO テスト |
| DASH-AUTH-004 | Shibboleth認証が有効な場合、システムはSAML 2.0プロトコルによる学術機関フェデレーション認証を提供しなければならない | 必須 | SAML テスト |
| DASH-AUTH-005 | 複数の認証プロバイダーが有効な場合、システムはログイン画面で認証方式選択UIを表示しなければならない | 必須 | UI テスト |
| DASH-AUTH-006 | システムは、認証プロバイダーごとに独立したユーザー属性マッピング設定を保持しなければならない | 必須 | 設定テスト |

#### 2.1.2 認証セキュリティ

| ID | EARS形式要件 | 優先度 | 検証方法 |
|----|-------------|--------|---------|
| DASH-AUTH-010 | ユーザーがログインを試行した場合、システムは多要素認証（MFA）オプションを提供しなければならない | 必須 | セキュリティテスト |
| DASH-AUTH-011 | ローカル認証使用時、システムはパスワードをArgon2idアルゴリズムでハッシュ化して保存しなければならない | 必須 | セキュリティテスト |
| DASH-AUTH-012 | 認証セッションが15分以上アイドル状態の場合、システムは自動的にセッションタイムアウト警告を表示しなければならない | 必須 | 機能テスト |
| DASH-AUTH-013 | 認証に3回連続で失敗した場合、システムは当該アカウントを30分間ロックしなければならない | 必須 | セキュリティテスト |
| DASH-AUTH-014 | ゲストアクセスが有効な場合、システムは制限付き読み取り専用モードを提供しなければならない | 任意 | 機能テスト |
| DASH-AUTH-015 | ローカル認証使用時、システムはパスワードリセット機能（メールによるワンタイムリンク）を提供しなければならない | 必須 | 機能テスト |
| DASH-AUTH-016 | システムは、すべての認証イベント（ログイン成功/失敗、ログアウト、セッション更新）を監査ログに記録しなければならない | 必須 | 監査テスト |

## 3. ワークフローテンプレート要件（WKFL）

### 3.1 テンプレート共通要件（WKFL-COMM）

| ID | EARS形式要件 | 優先度 | 検証方法 |
|----|-------------|--------|---------|
| WKFL-COMM-001 | システムは、各ワークフローテンプレートに対して以下のメタデータを保持しなければならない：テンプレートID、名前、説明、対象分野、必要入力データ、出力データ形式、推定実行時間、難易度レベル | 必須 | メタデータ検証 |
| WKFL-COMM-002 | システムは、ワークフローテンプレートのバージョン管理機能を提供しなければならない | 必須 | バージョン管理テスト |

| WKFL-COMM-004 | システムは、ワークフローの各ステップに対して「スキップ」オプションを提供しなければならない（必須ステップを除く） | 推奨 | カスタマイズテスト |
| WKFL-COMM-005 | ワークフロー実行中にエラーが発生した場合、システムは失敗したステップから再実行するオプションを提供しなければならない | 必須 | リカバリーテスト |

| WKFL-COMM-007 | ユーザーがワークフローをカスタマイズした場合、システムは「マイテンプレート」として保存する機能を提供しなければならない | 推奨 | テンプレート保存テスト |

| WKFL-DRUG-007 | ワークフロー完了時、システムは候補化合物を結合親和性スコア順にランキング表示しなければならない | 必須 | 出力検証テスト |
| WKFL-DRUG-008 | 出力において、システムは各候補分子のSMILES表記、2D構造図、予測特性テーブルを提供しなければならない | 必須 | 出力形式テスト |
| WKFL-DRUG-009 | システムは、結果をSDF、CSV、JSON形式でエクスポートする機能を提供しなければならない | 必須 | エクスポートテスト |

## 20. 付録

### 20.1 用語集

| 用語 | 定義 |
|------|------|
| EARS | Easy Approach to Requirements Syntax。要件を構造化された形式で記述するためのテンプレート |
| ワークフロー | 複数のステップで構成される一連の処理パイプライン |
| 基盤モデル | 大規模データで事前訓練された汎用AIモデル（MatterGen、Aurora等） |
| DFT | 密度汎関数理論。量子力学に基づく電子構造計算手法 |
| ADMET | 吸収(Absorption)、分布(Distribution)、代謝(Metabolism)、排泄(Excretion)、毒性(Toxicity)の略 |

| ナレッジグラフ | エンティティ（実体）とその関係をグラフ構造で表現した知識ベース |
| スクリーニング | 大量の候補から条件に合致するものを選別する絞り込みプロセス |
| ファネル | 各段階での候補数の減少を漏斗状に可視化したもの |
| 能動学習 | ユーザーフィードバックを基にモデルを反復的に改善する機械学習手法 |
| ベイズ最適化 | 確率的サロゲートモデルを用いて効率的に最適解を探索する手法 |
| 獲得関数 | ベイズ最適化において次のサンプル点を選択するための関数（EI、UCB等） |
| アレアトリック不確実性 | データ固有のノイズに起因する削減不可能な不確実性 |

| 反実仮想説明 | 「何が変われば予測結果が変わるか」を示す説明可能AI手法 |
| 21 CFR Part 11 | FDAの電子記録・電子署名に関する規制要件 |
| GxP | GLP（優良試験所規範）、GMP（優良製造規範）等の規制総称 |

| ChEMBL | 創薬関連の生物活性データベース |
| PubChem | 化学物質と生物活性の公開データベース |
| Materials Project | 計算材料科学データベース |
| FAIR原則 | Findable、Accessible、Interoperable、Reusableの略。データ共有のための原則 |
| マルチモーダルAI | 画像、テキスト、数値など複数種類のデータを統合して処理するAI |
| HPC | High Performance Computing。高性能計算。スーパーコンピュータ等を指す |
| Slurm | HPCクラスタ向けジョブスケジューラ |

## 21. プラグインアーキテクチャ要件（PLUG）

### 21.1 プラグインシステム基盤（PLUG-CORE）

| ID | EARS形式要件 | 優先度 | 検証方法 |
|----|-------------|--------|---------|
| PLUG-CORE-001 | システムは、研究分野固有の機能を独立したプラグインとして実装可能なアーキテクチャを提供しなければならない | 必須 | アーキテクチャレビュー |
| PLUG-CORE-002 | システムは、プラグインの登録・発見・読み込み・アンロードのライフサイクルを管理しなければならない | 必須 | ライフサイクルテスト |
| PLUG-CORE-003 | システムは、以下のプラグインタイプをサポートしなければならない：ドメインプラグイン、ワークフローステップ、データコネクタ、可視化、モデルアダプタ | 必須 | プラグインテスト |
| PLUG-CORE-004 | プラグインが追加された場合、システムは再起動なしでプラグインを動的に読み込まなければならない（ホットプラグ対応） | 推奨 | 動的読込テスト |
| PLUG-CORE-005 | システムは、プラグインのバージョン互換性を検証し、非互換プラグインの読み込みを拒否しなければならない | 必須 | 互換性テスト |
| PLUG-CORE-006 | システムは、プラグインごとに独立した設定スキーマを定義・検証できなければならない | 必須 | スキーマテスト |
